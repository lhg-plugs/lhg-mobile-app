# lhg-ma-cross：跨端方案选型方法论

## 1. 何时使用

- MVP 规划阶段，需要决定"用什么技术做 App"时
- 团队在"原生双端 / 混合 / 跨端框架"之间摇摆不定时
- 复盘：已选方案出现明显水土不服，需要重新评估时

**不适用**：只做单一平台（如只要 iOS 版）的项目；纯技术预研。

**边界**：本 skill 给的是"选型思路对比"，不是"一键生成 App"；最终技术决策由用户团队负责。

## 2. 输入与输出

**输入**：团队技术背景、预算与时间约束、性能敏感度、发布节奏要求。
**输出**：五维对比表 + 选型建议（含理由与代价说明）。

## 3. 方案全景（三类思路）

### 3.1 原生双端

iOS 与 Android 各用官方技术栈独立开发。

- 优点：性能最优、系统新特性跟进最快、体验上限最高
- 代价：两套代码、两个团队（或一人双修）、成本最高、发布最慢

### 3.2 混合方案（以 Capacitor 类思路为代表）

Web 技术（HTML/CSS/JS）打包为原生壳，通过桥接调用原生能力。

- 优点：团队有 Web 背景即可上手、一套代码多端、发布最快、热更新方便
- 代价：重度动画/复杂手势性能吃力、部分原生能力依赖插件、包体积偏大

### 3.3 跨端框架（以 Flutter 类思路为代表）

一套语言/框架编译或渲染到多端，自绘 UI 或转译为原生组件。

- 优点：一套代码、性能接近原生、UI 一致性好
- 代价：需要学习新语言/框架、包体积大、某些平台特性跟进慢、招人相对难

## 4. 五维对比表（选型时逐项打分）

| 维度 | 原生双端 | 混合方案 | 跨端框架 |
|---|---|---|---|
| 开发成本 | 高（两套人力） | 低（Web 团队可直接上） | 中（需学新栈） |
| 性能上限 | 最高 | 中（复杂动效吃力） | 高（接近原生） |
| 长期维护 | 两套代码各自维护 | 一套代码 + 桥接层 | 一套代码 |
| 发布时间 | 最慢 | 最快 | 中 |
| 团队技能要求 | 双端原生能力 | Web 能力即可 | 新框架学习成本 |

打分方法：每个维度按你的约束标"关键/一般/不重要"，关键维度一票否决。

## 5. 选型决策树

1. **要快速验证想法（4-8 周上线）且团队是 Web 背景** → 混合方案
2. **性能敏感**（游戏、音视频编辑、复杂动效、AR）→ 原生双端
3. **长期重投入、追求一套代码 + 接近原生体验** → 跨端框架
4. **只有 iOS 或只有 Android 用户** → 对应单端原生，别折腾跨端
5. **团队两种能力都有、预算充足** → 原生双端（体验上限最高）

## 6. 配套决策（选型时一并定）

- **消息推送**：选哪家推送服务（影响到达率与合规）
- **热更新**：发版节奏要求？紧急 bug 能否不经商店审核热修复
- **登录与鉴权**：手机号/第三方登录，token 方案
- **数据同步**：本地缓存 + 云端备份策略（换机、断网场景）

## 7. 反模式（不要这么做）

1. **追流行选型**："大家都在用 Flutter 所以我们也用" —— 按约束选，不按流行选。
2. **只谈优点不谈代价**：任何方案都有代价，选型报告必须写"代价"一节。
3. **跨端解决一切幻想**："一套代码"不等于"零原生工作"，桥接与平台适配永远存在。
4. **选型无理由**：只写结论不写理由 —— 三个月后没人记得为什么这么选。
5. **承诺式选型**："选这个能一键上架" —— 技术选型与过审无关，不许这么写。

### 4.1 打分示例（walkthrough）

假设：3 人 Web 背景小团队，8 周内验证一个记账 App 想法，性能要求一般。

| 维度（权重） | 原生双端 | 混合方案 | 跨端框架 |
|---|---|---|---|
| 开发成本（关键） | ✗ 两套人力，3 人不够 | ✓ Web 技能直接上 | △ 需 2-3 周学新栈 |
| 发布时间（关键） | ✗ 最慢 | ✓ 最快 | △ 中 |
| 性能上限（一般） | ✓ | △ 记账场景够用 | ✓ |
| 长期维护（一般） | ✗ 两套代码 | ✓ | ✓ |

结论：混合方案。关键维度一票否决，原生在"成本/时间"两个关键维度出局。

### 6.5 桥接与插件生态检查（混合/跨端方案必查）

1. 列出 App 需要的原生能力（推送、相册、定位、分享、支付）
2. 逐个确认：官方/社区有没有成熟插件？最近更新时间？issue 是否有人维护？
3. 没有现成插件的能力，评估自研桥接成本（按"人天"估，写进计划）
4. **红线**：核心功能依赖一个"三年没更新"的插件 → 换方案或自研

### 6.6 迁移预案（选错了怎么切）

- 混合 → 原生：业务逻辑多在 Web 层，壳可替换；提前把"原生能力调用"收敛到统一的桥接层，别散落在各处
- 跨端框架 → 原生：UI 层重写代价最大；MVP 阶段接受这个风险，写进"已知风险"
- 选型报告里加一节"如果选错了"，写清迁移代价上限（如"重写不超过 4 周"），超出就别选

## 7.5 常见问题

**Q：团队只会 Web，能做 App 吗？**
A：能，混合方案就是为这个场景设计的。但先确认需要的原生能力都有成熟插件（见 6.5）。

**Q：Flutter 和混合方案怎么二选一？**
A：看两个条件：①团队愿不愿意学新语言（不愿意→混合）；②对性能/体验上限要求高不高（高→Flutter 或原生）。两个都满足不了就选混合先验证。

**Q：先做 iOS 还是双端一起？**
A：MVP 阶段看用户在哪：如果 80% 目标用户是 iPhone，先单端验证更快。跨端方案的优势是"一套代码"，但测试与上架仍是双份工作，别低估。

**Q：选型错了能换吗？**
A：能，但有代价。见 6.6 迁移预案：提前把原生能力收敛到统一桥接层，换方案时只换壳不换业务。

**Q：要不要一开始就做深色模式/多语言？**
A：MVP 阶段不做。这些是典型的 P1 功能：有用，但不验证核心假设。先验证假设，再补体验。
